# Денежные операции и отчётность

## Модель операции

[MoneyMovement](../../CostVision.Domain/Models/MoneyMovements/MoneyMovement.cs) принадлежит одному `Account` и хранит:

- положительную сумму с precision `18,2`;
- тип `Expense` или `Income`;
- пользовательский момент операции;
- редактируемый комментарий и отдельный исходный комментарий импорта;
- автора и исполнителя;
- даты создания/обновления;
- источник `Manual` или `BankStatementImport`;
- связи с чеками.

Ручная factory допускает отрицательную входную сумму только как способ вывести тип по умолчанию; в сущности сохраняется абсолютное значение. При явном типе он проверяется как известный enum. Импорт требует строго положительную сумму и непустой нормализованный исходный текст выписки.

## Ручные операции

[CreateMoneyMovementUseCase](../../CostVision.Application/UseCases/MoneyMovements/Management/CreateMoneyMovementUseCase.cs) требует membership Owner/Editor. Исполнителем по умолчанию становится текущий пользователь; другой исполнитель обязан быть участником того же счёта.

После создания расхода use case пытается сразу найти чек с той же календарной датой, суммой и счётом. Связь создаётся только при единственном несвязанном кандидате с каждой стороны.

Операцию можно перенести в другой редактируемый счёт, удалить или изменить её комментарий. Эти сценарии повторно проверяют доступ к текущему и, при переносе, целевому счёту. Источник импорта и исходный комментарий при обычном редактировании не подменяются пользовательским текстом.

## Поддерживаемый PDF-импорт

Registry содержит parser’ы Т-Банка, СберБанка и Альфа-Банка. Каждый parser объявляет собственный `bankId`, описание формата и правила распознавания. [BankStatementPdfTextExtractor](../../CostVision.Infrastructure/Services/MoneyMovements/BankStatementPdfTextExtractor.cs) использует PdfPig и возвращает текст по страницам.

[PreviewBankStatementImportUseCase](../../CostVision.Application/UseCases/MoneyMovements/BankStatementImports/PreviewBankStatementImportUseCase.cs) выполняет:

1. выбор настроенного parser по `bankId`;
2. проверку допустимого имени/формата файла;
3. проверку Owner/Editor доступа к счёту;
4. извлечение текстового слоя;
5. parsing строк и формирование ошибок;
6. поиск существующих импортированных операций в диапазоне дат;
7. отметку дублей в БД и внутри preview.

PDF без текста отклоняется. Если parser не нашёл ни строк, ни собственных ошибок, ответ содержит диагностический фрагмент первых нормализованных строк PDF; полное содержимое файла не сохраняется.

## Ключ дубля и сохранение

Дубль банковской строки определяется внутри счёта по точному набору:

`OccurredAt + Amount + Type + ImportComment`.

[ImportMoneyMovementsUseCase](../../CostVision.Application/UseCases/MoneyMovements/BankStatementImports/ImportMoneyMovementsUseCase.cs) повторно валидирует присланные строки, не доверяя preview с клиента. Дубли без `ReplaceDuplicate` пропускаются с line error. При подтверждённой замене существующая импортированная операция обновляется доменным методом. Все допустимые изменения выполняются внутри одной транзакции; результат отдельно сообщает created, updated и errors.

## Связь операции и чека

`MoneyMovementReceipt` имеет составной ключ `(MoneyMovementId, ReceiptId)`, автора связи и UTC-время создания. Одна и та же пара не дублируется. Модель разрешает несколько разных связей; автоматический алгоритм намеренно работает только с полностью свободными объектами.

Ручная связь требует:

- редактируемую операцию;
- доступный чек;
- общий счёт операции и чека либо собственный чек без счёта;
- отсутствие уже существующей пары.

Отвязка также требует mutation-доступ к счёту операции. Кандидаты загружаются с server-side pagination и фильтрами, а не передаются клиенту целиком.

## Массовая точная сверка

[AutoLinkExactMoneyMovementReceiptsUseCase](../../CostVision.Application/UseCases/MoneyMovements/ReceiptLinks/AutoLinkExactMoneyMovementReceiptsUseCase.cs) рассматривает за период только:

- несвязанные расходы;
- несвязанные чеки операции `Income`;
- доступные пользователю данные;
- при заданном фильтре — один счёт.

Ключ — календарная дата, сумма и `AccountId`. Связь появляется, только если после исключения уже занятых объектов в группе остаются одна операция и один чек. Массовое создание выполняется транзакционно. Неоднозначность не является ошибкой и даёт ноль связей для группы.

## Dashboard доходов и расходов

[GetDashboardIncomeExpenseReportUseCase](../../CostVision.Application/UseCases/Dashboard/GetDashboardIncomeExpenseReportUseCase.cs) принимает диапазон включительных дат, группировку `day`/`month`, account filters, `IncludeWithoutAccount`, store filters и источник расходов.

Доход всегда строится по `MoneyMovementType.Income`. Расход поддерживает режимы:

- `receipts` — суммы чеков;
- `moneyMovements` — расходные операции;
- `receiptsAndMoneyMovements` — операции плюс чеки, у которых нет связанного расхода в выбранном периоде.

Это правило предотвращает двойной учёт сверенной покупки. Ряд заполняется непрерывно от начала до конца периода, включая нулевые точки. Store filter применяется к расходной части: у самостоятельного дохода нет магазина. Список магазинов собирается из доступных чеков и чеков, связанных с операциями.

Выбор отображаемого магазина: адаптивное название, исходное название, продавец из чека, затем «Без магазина».
