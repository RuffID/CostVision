# Обзор системы

## Назначение

CostVision — ASP.NET Core Razor Pages-приложение для учёта покупок по фискальным чекам и денежных операций. Оно объединяет три потока: получение состава чека через внешний API, ручной или банковский учёт движений денег и сверку расходов с покупками. Dashboard строит временной ряд доходов и расходов без двойного учёта связанных данных.

## Состав решения

| Проект | Ответственность | Проектные зависимости |
|---|---|---|
| `CostVision.Domain` | Сущности, enum и инварианты | нет |
| `CostVision.Application` | Use case, DTO, запросы, `ServiceResult`, контракты репозиториев и сервисов | `Domain` |
| `CostVision.Infrastructure` | EF Core/SQL Server, репозитории, внешний API чеков, PDF и фоновые службы | `Application`, `Domain` |
| `CostVision.Web` | Composition root, Razor Pages, JSON handlers, cookie-авторизация и TypeScript UI | все основные слои |

Тестовые проекты разделены на `Application.UnitTests`, `Infrastructure.UnitTests`, `Infrastructure.IntegrationTests` и `Web.UnitTests`.

## Технологический стек

- .NET 10, ASP.NET Core Razor Pages и controllers;
- Entity Framework Core 10 и Microsoft SQL Server;
- cookie authentication и ASP.NET Core Data Protection;
- Serilog с консольным и файловым выводом;
- TypeScript 6 в strict-режиме, ES2020 и Bootstrap UI;
- PdfPig для извлечения текста банковских PDF;
- Newtonsoft.Json и HTTP-клиент для сервиса `proverkacheka.com`;
- xUnit v3, Moq и Testcontainers for SQL Server;
- multi-stage Docker build на образах .NET 10.

Актуальные версии находятся в `.csproj` и [package.json](../../CostVision.Web/package.json).

## Главные потоки

### Добавление и обогащение чека

1. [AddReceiptModel](../../CostVision.Web/Pages/AddReceipt.cshtml.cs) принимает QR-результаты или ручную форму.
2. Application проверяет право добавления в счёт и уникальность чека.
3. Основные фискальные реквизиты сохраняются сразу.
4. [ReceiptRefreshWorkflow](../../CostVision.Application/UseCases/Receipts/Receipts/Refresh/ReceiptRefreshWorkflow.cs) получает подробности у внешнего провайдера, разрешает магазин и товары и атомарно обновляет граф чека.
5. Необогащённые чеки повторно запрашивает фоновая служба по ежедневному расписанию.

### Импорт и сверка денежных операций

1. Пользователь выбирает поддерживаемый банк, счёт и PDF.
2. Текст извлекается постранично, профильный parser формирует предпросмотр.
3. Дубликаты отмечаются по устойчивому ключу операции.
4. Подтверждённые строки сохраняются транзакционно.
5. Точные однозначные пары «дата + сумма + счёт» связываются с чеками автоматически; остальные доступны для ручной сверки.

## Осознанные границы

- Банк не является online-интеграцией: принимаются пользовательские PDF-файлы.
- Внешний сервис чеков — источник подробностей, но базовая запись чека создаётся локально из QR или формы.
- Один чек может быть связан с несколькими счетами, денежная операция принадлежит ровно одному счёту.
- Общая роль Admin управляет пользователями; доступ к финансовым данным по-прежнему ограничивается владением чеком и участием в счёте.
- `ExpenseCategory` присутствует в Domain и EF-модели, но application/web use case управления категориями отсутствуют.
- Приложение применяет ожидающие EF migrations при старте после обязательного backup. Это эксплуатационное решение следует учитывать при выдаче прав SQL-пользователю.
