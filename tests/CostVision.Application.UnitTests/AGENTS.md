# Общие фабрики application-тестов

## Ответственность

Фабрики создают пользователей, счета, чеки, операции и mock UoW; GlobalUsings задаёт общие импорты.

## Контракты и границы

Stage02RegressionTests выполняет реальные predicate-выражения над графами для каталога, ролей, входа и счетов; проверяет отказ до мутации/сохранения, архивную границу и owner membership. Include и SQL им не подтверждаются. TestUnitOfWorkFactory получает существующие role ID явно; пустой default не означает существование любой роли.

Новый default не должен скрывать значимое условие сценария. Linked compile и фабрики сверять со всеми потребителями; не превращать mock-тесты в доказательство SQL.

Stage03RegressionTests исполняет реальные предикаты над снимком сохранённых данных, который не содержит pending Create/связей; поэтому повторный запрос не может подменить локальную дедупликацию. Проверяются результаты строк, графы, отказ без записи, ru-RU/en-US, перенос, группировка и восстановление связей при ошибке. TestUnitOfWorkFactory.SetupReceiptTransaction принимает только Serializable и не выполняет неявный SaveChanges. Тесты не доказывают SQL-гонки.

Stage04RegressionTests проверяет импорт, ID/ключ/источник/счёт, счётчики/ошибки, ru-RU/en-US, роли, оба переноса, общий точный matcher и ручные множественные связи. Pending Create не виден запросам до SaveChanges. FK owner membership согласуется с назначенным ID тестовой фабрики как имитация EF fixup; это не изменение production-контракта. Serializable-заглушка не сохраняет автоматически и не доказывает конкуренцию SQL.

Stage07RegressionTests и ProjectedReadTestFactory исполняют actual predicate/projection над доменными графами: root-фильтры, полные totals/count, устойчивые страницы, группы магазинов/документов, page-only счётчики, точное расстояние дат и границы страниц. Наблюдение root reads обязательно непустое; оно не выдаётся за число SQL-строк. Прежние регрессии 01–06 используют тот же финансовый контракт.

## Проверка

Stage06RegressionTests проверяет точную identity, подготовку до мутации, timeout/отмену, отказ применения/хранения, RowVersion, увеличение RefreshRevision при совпадающих реквизитах/времени, доступ до записи, ручное восстановление и реальные агрегаты успешного workflow. Stage06BatchTests выполняет actual workflow с настоящими DI scopes и подставными predicate-репозиториями: пакеты 32/3, продолжение после ошибки, отсутствие переноса pending-каталога в следующий scope, retry-state в новом scope, семь неизвестных отказов, ошибку записи retry-state, конфликт каталога и async disposal. Снимки scalar retry-state имитируют материализацию только в тестовой модели; их tracker/commit-модель и часы не доказывают EF fixup, SQL rollback/конкурентность или реальный hosted lifecycle.

Stage05RegressionTests проверяет конкретные суммы всех источников/направлений, покрытие нескольких документов/платежей по датам, identity, фильтры и отказ доступа, согласованность агрегатов списка/деталей/refresh, кандидатов и единицы. Подставные репозитории исполняют переданные predicates. Обратная Store.Receipts навигация наполняется только в тестовом графе как имитация EF materialization; это не доказательство SQL include, snapshot или отзыва membership между чтениями.

Проверять тестовые утверждения и границы их изоляции; запуск выбирать по правилам родительского AGENTS.md. Не ослаблять ожидания и не сообщать о прохождении без выполнения.
