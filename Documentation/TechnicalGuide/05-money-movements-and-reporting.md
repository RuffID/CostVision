# Денежные операции и отчётность

## Модель операции

[MoneyMovement](../../CostVision.Domain/Models/MoneyMovements/MoneyMovement.cs) принадлежит одному `Account` и хранит:

- положительную сумму с precision `18,2`;
- тип `Expense` или `Income`;
- пользовательский момент операции;
- редактируемый комментарий и отдельный исходный комментарий импорта;
- автора и исполнителя;
- даты создания/обновления;
- источник `Manual` или `BankStatementImport`;
- связи с чеками.

Ручная factory допускает отрицательную входную сумму только как способ вывести тип по умолчанию; в сущности сохраняется абсолютное значение. При явном типе он проверяется как известный enum. Импорт требует строго положительную сумму и непустой нормализованный исходный текст выписки.

## Ручные операции

[CreateMoneyMovementUseCase](../../CostVision.Application/UseCases/MoneyMovements/Management/CreateMoneyMovementUseCase.cs) требует membership Owner/Editor. Исполнителем по умолчанию становится текущий пользователь; другой исполнитель обязан быть участником того же счёта.

Общий валидатор получает requireActive=true, загружает Account и отклоняет IsArchived до открытия транзакции. Архивное правило не добавляется автоматически в сценарии изменения исторических комментариев, удаления, переноса или связей.

После создания расхода use case пытается сразу найти чек с той же календарной датой, суммой и счётом. Связь создаётся только при единственном несвязанном кандидате с каждой стороны.

Создание выполняется в Serializable-перегрузке UoW: явный SaveChanges даёт ID операции, общий ExactMoneyMovementReceiptMatcher читает кандидатов, второй SaveChanges выполняется только при найденной связи. Автоматическое дополнительное сохранение этой перегрузкой не выполняется.

Операцию можно перенести в другой редактируемый счёт, удалить или изменить её комментарий. Эти сценарии повторно проверяют доступ к текущему и, при переносе, целевому счёту. Источник импорта и исходный комментарий при обычном редактировании не подменяются пользовательским текстом.

Перенос загружает ReceiptLinks/Receipt/Accounts внутри Serializable и проверяет совместимость всех связей до изменения AccountId. Требуется целевой счёт у чека либо собственный чек без счетов. Несовместимость возвращает Conflict до записи; необходима ручная отвязка. Для импортной операции дополнительно проверяется отсутствие того же ключа в target. Перенос чека проверяет будущий набор его счетов в той же границе; молчаливого удаления связей нет.

## Поддерживаемый PDF-импорт

Registry содержит parser’ы Т-Банка, СберБанка и Альфа-Банка. Каждый parser объявляет собственный `bankId`, описание формата и правила распознавания. [BankStatementPdfTextExtractor](../../CostVision.Infrastructure/Services/MoneyMovements/BankStatementPdfTextExtractor.cs) использует PdfPig и возвращает текст по страницам.

[PreviewBankStatementImportUseCase](../../CostVision.Application/UseCases/MoneyMovements/BankStatementImports/PreviewBankStatementImportUseCase.cs) выполняет:

До перечисленных действий сценарий проверяет FileStream/FileLength нейтрального PreviewBankStatementImportRequest. Отсутствующий поток или неположительная длина даёт прежнее Validation «Выберите файл выписки.». HTTP-адаптер владеет и освобождает поток; use case не закрывает его и не знает PageModel. После parser проверяется вычислимость следующего дня каждой даты строки до поиска дублей. Алгоритм и права предпросмотра сохранены.

1. выбор настроенного parser по `bankId`;
2. проверку допустимого имени/формата файла;
3. проверку Owner/Editor доступа к счёту;
4. извлечение текстового слоя;
5. parsing строк и формирование ошибок;
6. поиск существующих импортированных операций в диапазоне дат;
7. отметку дублей в БД и внутри preview.

PDF без текста отклоняется. Если parser не нашёл ни строк, ни собственных ошибок, ответ содержит диагностический фрагмент первых нормализованных строк PDF; полное содержимое файла не сохраняется.

## Ключ дубля и сохранение

Дубль банковской строки определяется внутри счёта по точному набору:

`OccurredAt + Amount + Type + ImportComment`.

[ImportMoneyMovementsUseCase](../../CostVision.Application/UseCases/MoneyMovements/BankStatementImports/ImportMoneyMovementsUseCase.cs) повторно валидирует присланные строки, не доверяя preview с клиента. Дубли без `ReplaceDuplicate` пропускаются с line error. При подтверждённой замене существующая импортированная операция обновляется доменным методом. Допустимые изменения выполняются внутри одной транзакции; результат отдельно сообщает created, updated и errors.

[BankStatementRowKey](../../CostVision.Application/UseCases/MoneyMovements/BankStatementImports/BankStatementRowKey.cs) используется в preview, локальном индексе принятых строк и серверном предикате импорта/переноса. В ключе нет ID операции или счёта; поиск размещения добавляет AccountId и Source. Decimal и DateTime сравниваются как значения, текст — ordinal после Trim. Перед записью сумма проверяется на точное представление в 18,2. SQL-колляция не считается подтверждением равенства: найденная запись повторно сверяется типизированным ключом.

DuplicateMoneyMovementId должен совпасть с единственным полным дублем в счёте. Неверный ID не вызывает fallback, создания или изменения другой операции. Несколько существующих дублей дают ошибку ручной сверки. TryReplaceFromBankStatement защищает Source и полное равенство ключа; меняет только Comment и UpdatedAtUtc. Локальный индекс содержит только принятые строки и видит pending-операцию до SaveChanges. Created/Updated — счётчики принятых строк; new/replace/new даёт 2/1/0 и две операции. Проверки дубля и явная запись находятся внутри Serializable; без принятых изменений SaveChanges не вызывается.

До обработки строк сервер повторно проверяет membership Owner/Editor и действующий счёт. Архив возвращает Forbidden без транзакции или мутации, включая ReplaceDuplicate. Предпросмотр не вводит новый архивный запрет и не является разрешением сохранения.

Уникального ограничения импортного ключа в EF-модели нет. Serializable удерживает проверяемые диапазоны до commit в сценарном протоколе; отсутствие гонки ещё требует двух соединений SQL Server. Клиентское окно показывает счётчики и ошибки, сохраняет непринятые/неотправленные строки, удаляет принятые clientRowId до reload и не закрывается автоматически. LineNumber сохранения переводится в sourceLineNumber PDF. Ошибка полного дубля содержит CanReplaceDuplicate и при доступном ID — DuplicateMoneyMovementId; UI предлагает явное обновление комментария. Успешный ServiceResult не означает сохранение всех строк.

## Связь операции и чека

`MoneyMovementReceipt` имеет составной ключ `(MoneyMovementId, ReceiptId)`, автора связи и UTC-время создания. Одна и та же пара не дублируется. Модель разрешает несколько разных связей; автоматический алгоритм намеренно работает только с полностью свободными объектами.

Ручная связь требует:

- редактируемую операцию;
- доступный чек;
- общий счёт операции и чека либо собственный чек без счёта;
- отсутствие уже существующей пары.

Отвязка также требует права изменения счёта операции. Оба сценария кандидатов возвращают PagedListDto с count и флагами страниц. Размер по умолчанию 20, границы 1–100; страница ограничивается фактическим count. Операции сортируются по точному расстоянию даты, суммы и ID до Skip/Take. Обратный список выбирает страницы документов ReceiptIdentity, затем все подходящие копии этих документов: count/pageSize относятся к документам, Items может содержать больше копий. Порядок групп сохраняет порядок ID страницы.

Ручная привязка читает операцию, совместимость чека и существование пары внутри Serializable и сохраняет явно. Это необходимо для координации с переносом и автоматической сверкой; свободность обеих сторон от неё не требуется, разные ручные пары по-прежнему разрешены.

Список операций и счётчики кандидатов требуют текущего владения/участия в счёте. Авторство операции не даёт доступа после исключения. Чтение связей со стороны чека дополнительно фильтрует каждую операцию; в обратном направлении отдельно проверяется доступ к каждому связанному чеку. DTO не раскрывают недоступные суммы, комментарии, названия счетов и агрегаты. Название счёта связанного чека выбирается только среди доступных счетов. Мапперы обоих направлений и MoneyMovementMapper получают явный ID текущего пользователя; include загружают необходимые Accounts/Members.

Признаки связанности в DTO кандидатов учитывают только доступные связанные объекты. Условие исключения уже занятых объектов из подбора и точной автоматической сверки сохранено. Изоляция этапа 01 проверена предикатами над доменными графами и DTO; SQL Server приёмка ещё не выполнена. Целостность импорта и записи связей уточнена этапом 04 выше; расчёт этапа 05 описан ниже.

ReceiptMoneyMovementCandidateRules общий для GetReceiptMoneyMovementCandidatesUseCase и ReceiptReportCandidateCounts. Отчётный счётчик соответствует начальному UI-запросу: [начало дня−1; начало дня+2), допуск суммы 1, ExcludeLinked=true, оба типа движения. Проверяется реальная копия по открываемому ReceiptId, её Accounts и текущий доступ к счёту операции. Собственный чек действительно без счетов допускает свои операции доступных счетов; скрытые Accounts не превращают его в такой чек. Viewer читает кандидатов, Owner/Editor создают связь. Общий matcher свободных Expense/Income-чеков этапа 04 и ручные множественные пары не изменены.

## Массовая точная сверка

[AutoLinkExactMoneyMovementReceiptsUseCase](../../CostVision.Application/UseCases/MoneyMovements/ReceiptLinks/AutoLinkExactMoneyMovementReceiptsUseCase.cs) рассматривает за период только:

- несвязанные расходы;
- несвязанные чеки операции `Income`;
- операции счетов с явной Owner/Editor membership и доступные чеки;
- при заданном фильтре — один счёт.

Общий [ExactMoneyMovementReceiptMatcher](../../CostVision.Application/UseCases/MoneyMovements/ReceiptLinks/ExactMoneyMovementReceiptMatcher.cs) сравнивает календарную дату, сумму и общий AccountId. Связь появляется при одном кандидате с каждой стороны исходного набора; обработка не превращает неоднозначность в выбор порядком обхода. При фильтре одного счёта рассматривается его набор; без фильтра несколько подходящих операций разных счетов одного чека дают неоднозначность. Viewer отсекается SQL-предикатом роли. Все чтения и явная запись выполняются внутри Serializable. Неоднозначность даёт ноль связей. Use case зарегистрирован в DI, но PageModel его не вызывает; отдельной массовой команды интерфейса нет. SQL-конкурентность не подтверждена mock-тестами.

## Dashboard доходов и расходов

Список MoneyMovements возвращает MoneyMovementListDto со scalar-страницей и отдельными totalCount/incomeSum/expenseSum всего фильтра. Период, доступ, выбранный счёт, поиск по Comment/ImportComment и фильтр видимых связей применяются до агрегатов и страницы. Сортировка OccurredAt DESC/Id; memberships используются в predicates без материализации. AvailableReceiptCount рассчитывается лишь для показанных операций по прежнему точному правилу календарной даты/суммы/счёта и свободных доступных копий.

Dashboard читает отдельный DISTINCT-каталог магазинов и минимальные scalar-проекции реквизитов/ID связей. Неиспользуемый источник не читается. Для точного глобального покрытия остаются все выбранные scalar-документы, платежи и рёбра; ограничения страницы или приблизительной SQL-суммы к алгоритму покрытия нет. Графы счетов/участников/истории не материализуются. Несколько чтений не получают общий snapshot.

[GetDashboardIncomeExpenseReportUseCase](../../CostVision.Application/UseCases/Dashboard/GetDashboardIncomeExpenseReportUseCase.cs) принимает диапазон включительных дат, группировку `day`/`month`, account filters, `IncludeWithoutAccount`, store filters и источник обоих направлений. Имя поля ExpenseSource сохранено для совместимости.

Чистый IncomeExpenseReportCalculator получает уже ограниченные доступом/периодом/счетами/магазинами ReportReceipt и ReportMoneyMovement:

- `receipts` — только документы Receipt в обоих направлениях;
- `moneyMovements` — только операции в обоих направлениях;
- `receiptsAndMoneyMovements` — операции целиком и непокрытая часть документов того же направления по существующим связям.

ReceiptFinancialRules задаёт Income/RefundExpense → расход, RefundIncome/Expense → доход. Номиналы положительные, IncomeSum и ExpenseSum раздельные: покупка 1000/возврат 300 дают 1000/300. Неизвестный enum вызывает явную ошибку. Use case группирует копии по типизированному GetIdentity; объединяет ID их связей. Реальные операции distinct по ID, не по дате/сумме. Выбранный счёт чека и текущий доступ проверяются внутри одного Accounts.Any.

ReceiptPaymentCoverage рассчитывает decimal-покрытие сетью остаточных ёмкостей: каждый рубль выбранной доступной операции используется один раз, документ покрывается не больше номинала. Документы активируются по DateTime, затем invariant identity key (ordinal); обратные рёбра позволяют перераспределение без потери ранее покрытых сумм. Платежи упорядочены по дате/ID. Связи и сущности не меняются. Остаток идёт на дату документа, весь платёж и переплата — на дату операции. Платежи вне периода, исключённых/недоступных счетов и другого направления не покрывают документ.

Примеры: 1000+400 дают 1000; 1000+400+600 дают 1000; 1000+700+700 дают 1400. Два разных документа по 1000 с общей оплатой 1000 дают 2000. Возврат 300 со связанным Income 300 даёт доход 300. Чек 1000 в понедельник/платёж 400 во вторник даёт 600/400 по дням. Одна identity через копии не удваивается; два реальных платежа одинаковой суммы/даты сохраняются.

Ряд включает нулевые дни/месяцы. Границы SQL: DateTime >= DateFrom.Date и < DateTo.Date+1. Store filter ограничивает расход; доходные документы/операции не урезаются. Каталог магазинов зависит от выбранного источника; связанный закрытый чек не раскрывает название и не удовлетворяет фильтр операции. Эти правила проверены изолированно, фактическая материализация, snapshot нескольких чтений и отзыв membership требуют SQL-приёмки.

Выбор отображаемого магазина: адаптивное название, исходное название, продавец из чека, затем «Без магазина».
