# Этап 08. Границы Application и сохранения

Статус: **Не начат**.
Приоритет: **П2**.
Зависимости: 01–07.

## Найденные проблемы

1. [IUnitOfWork](../../../CostVision.Application/Abstractions/DataBase/Repositories/IUnitOfWork.cs) объединяет 11 репозиториев. Даже чтение одного объекта получает всю поверхность приложения. Тестовые фикстуры вынуждены конструировать и настраивать большой набор зависимостей.
2. Application зависит от EF Core/Relational и `EFCoreLibrary.dll`. [AppDbContextBase](../../../CostVision.Application/Abstractions/DataBase/AppDbContextBase.cs) наследует `DbContext`; интерфейсы репозиториев включают context type, `IQueryable`, `include` и tracking-параметры. Это фактическая граница проекта, а не случайный отдельный `using`.
3. Domain использует `IEntity` из внешней DLL. Её независимость от EF нельзя утверждать без проверки контракта DLL. Источник, версия и совместимость двух DLL из `libs` не описаны рядом с поставкой.
4. [MoneyMovementsPageUseCase](../../../CostVision.Application/UseCases/MoneyMovements/Queries/MoneyMovementsPageUseCase.cs) объединяет 14 use case, в основном переадресует их и отражает структуру страницы. `PreviewBankStatementImportPageRequest` также именуется по web-экрану внутри Application.
5. [UnitOfWork](../../../CostVision.Infrastructure/DataBase/Repositories/UnitOfWork.cs) сам сохраняет в конце транзакции; отдельные сценарии вызывают сохранение внутри, чтобы получить ID и перечитать данные. Двойное сохранение может быть необходимым, поэтому удалять внутренний вызов механически нельзя. После rollback состояние change tracker этим методом явно не восстанавливается.

## План работ

- Начать с минимальных зависимостей чтения и сценарных UoW для групп записывающих операций. Все UoW одного scope должны использовать одну scoped-сессию; не создавать отдельный контекст на каждый репозиторий.
- Явно описать владельца транзакции, промежуточного сохранения и поведения после ошибки. Не переиспользовать повреждённую сессию в следующем сценарии.
- Упростить фасад страницы по реальной пользе: оставить координацию сценария, убрать механический набор прокси либо разделить его по обязанностям.
- Решение о полном удалении EF из Application принять отдельно до массового изменения контрактов. Действующий `AGENTS.md` разрешает композицию `predicate/include` вызывающим кодом и запрещает специализированные query-методы: не нарушать это правило под видом следования общему архитектурному скиллу.
- Проверить принятую DLL и её документацию перед проектированием adapter-контрактов. Не копировать её persistence, не придумывать отсутствующие методы и не менять library API незаметно.
- При изменении устойчивых границ обновить владеющий `AGENTS.md` после проверки, а не объявлять новую архитектуру уже существующей.

## Проверки и приёмка

- [ ] Read-only сценарии имеют минимальные зависимости; записывающие сценарии имеют явную транзакционную границу.
- [ ] Сохранена единая scoped-сессия и работоспособная DI-регистрация.
- [ ] Необходимые промежуточные сохранения сохранены и объяснены; rollback не приводит к последующей случайной записи.
- [ ] Нет новых специализированных методов репозитория или скрытого SQL.
- [ ] Архитектурное решение и фактические зависимости согласованы; тесты границ проверяют принятое правило.
