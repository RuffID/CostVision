## Порядок выполнения

1. Сначала закрыть этапы 01–06 небольшими изменениями с регрессионными проверками. Не объединять исправление прав, изменение финансовых правил и перестройку архитектуры в одну правку.
2. Затем выполнить 07 → 07A → 08 и этап 09. Оптимизацию запросов вести на исправленном контракте доступа и расчёта. Разделение UoW выделено в 07A; прежняя нумерация остальных этапов сохранена.
3. После этого выполнить 10–13, сохраняя AJAX-потоки, TypeScript и общий стек модалок.
4. До 14 выполнить 08A: согласованно обновить поставку EFCoreLibrary и все consumers, перейти на библиотечный maintenance и проверить отсутствие обходов. 08A можно реализовать отдельно от frontend 11–13, сохраняя их HTTP-контракты; приёмку на реальной БД не подменять изолированными результатами.
5. Завершить 14–15 на новой библиотечной границе. Проверки добавлять в соответствующий этап сразу; этап 15 не является разрешением отложить все тесты до конца.

Таблица задаёт зависимости, а не разрешает автоматически начинать реализацию. Каждый этап выполняется только после отдельной просьбы пользователя. Если обнаружен новый дефект, добавить его в соответствующий этап с путём, сценарием и проверкой, не расширяя незаметно текущую задачу.

## Как обновлять статус

Источник подробного статуса — файл этапа; таблица выше должна соответствовать ему. Допустимые значения: **Не начат**, **В работе**, **Заблокирован**, **Реализован, проверка не завершена**, **Завершён**.

При начале работ обновить статус и дату в файле этапа и в таблице. При завершении заполнить его журнал: что изменено, какие проверки выполнены, фактический результат, какие проверки не запускались и почему. Отмечать критерии только по проверенным результатам. Если для приёмки нужен SQL Server или браузер, изолированных тестов недостаточно для статуса «Завершён»; использовать «Реализован, проверка не завершена». При блокировке записать конкретную причину и следующий необходимый шаг.

## Общие ограничения

- Соблюдать корневой `AGENTS.md` и правила `CostVision.Web/Pages/AGENTS.md`.
- Сохранять базовые методы репозиториев; не добавлять методы вида `Get...With...` или `GetAccessible...` под отдельную выборку.
- Рекомендации о независимом от EF Application рассматриваются как отдельное архитектурное решение в этапе 08. Они не отменяют действующие правила композиции `predicate/include` на стороне вызывающего кода.
- Ручные правки делать точечно через `apply_patch`, сохранять кодировку и окончания строк. Не патчить generated-файлы.
- Миграции создаёт пользователь вручную. Изменение модели и необходимость миграции фиксировать в соответствующем этапе.
- Проверять конкретные `.csproj`, без запуска приложения и внешних зависимостей. Реальные БД, SQL, Docker, hosting, браузер и deployment требуют отдельного разрешения согласно правилам проекта.
- Не приписывать библиотекам из `libs` возможности, не проверенные по их фактическому контракту. Не подменять их скрытым fallback или собственным доступом к БД.
- Все описания, статусы и отчёты внутри плана писать на русском.
