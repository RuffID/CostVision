# Подбор кандидатов сверки

## Ответственность

Два сценария ищут чеки для операции и операции для чека; интерфейсы находятся в дочерней ReceiptLinks.

## Контракты и границы

Проверять доступ обеих сторон и совпадение счёта. Сейчас возвращаются полные наборы кандидатов; не описывать это как SQL-пагинацию.

Изменение операций, импорт и запись сверки принадлежат дочерним Management, BankStatementImports и ReceiptLinks. Их транзакционные правила нельзя переносить в PageModel или специализированные методы репозиториев. Открытые SQL-проверки сохраняются отдельно от unit-результатов.

Чтение исходного объекта и кандидатов ограничивается FinancialDataAccess; авторство операции не заменяет участие в её счёте. Маппинг требует явный ID текущего пользователя; название счёта чека и признаки связанных объектов учитывают отдельный доступ. Include должен загружать Account/Members объектов, необходимых для этих проекций. Правила даты, суммы, общего счёта и исключения уже занятых объектов не менять в рамках изоляции.

## Проверка

ReceiptMoneyMovementCandidateRules задаёт общий предикат getter и отчётных счётчиков. Начальное окно: день чека ±1 календарный день, сумма ±1, свободные операции обоих направлений. Счётчик использует реальную копию по открываемому UI ReceiptId и её Accounts, без объединения несовместимых счетов других копий. Viewer может читать кандидатов; запись связи по-прежнему требует Owner/Editor. Это ручной контракт, не точный автоматический matcher.

Подходящие изолированные проверки находятся в tests/CostVision.Application.UnitTests. Собирать конкретный затронутый .csproj по корневым правилам; mock-репозитории не подтверждают SQL.

После изменения исходников в этой папке сверить и актуализировать здесь ответственность, контракты, зависимости и способ проверки в рамках той же задачи. При переносе файлов обновить описания прежней и новой папок. Не добавлять фиктивный журнал или неподтверждённый результат проверки.
