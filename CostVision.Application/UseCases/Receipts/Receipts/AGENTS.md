# Создание, чтение и обновление чеков

## Ответственность

Сценарии принимают QR/ручной ввод, читают списки и детали, удаляют и запускают ручное/фоновое обновление.

## Контракты и границы

Manual/QR получают IReceiptCreationUnitOfWork (Receipt/ReceiptAccount); Delete получает Receipt + технический scope. Списки/детали/обёртка ручного refresh получают прямые repositories; helpers не владеют транзакцией.

Проверять доступ, пакетные повторы, фискальную идентичность и полное сохранение графа. SQL-уникальность не заменяет локальную дедупликацию QR-пакета.

Ручной ввод и QR используют ReceiptIdentityPredicates. В QR-пакете локальные ключи (ReceiptIdentity, AuthorId) и (ReceiptIdentity, AccountId) учитывают новые копии и связи до сохранения; повтор получает ErrorMessage и учитывается в ErrorCount. Авторская копия загружается с Accounts до TryAddAccount. Проверка дубля и запись находятся в одной Serializable-транзакции; SQL-приёмка блокировок остаётся обязательной. При ошибке сохранения/commit добавленные доменные связи отменяются, ответ не сообщает успешную пустую запись. Не переиспользовать scope хранения после отказа транзакции.

Списки группируют документы через GetIdentity. Итоги полного отфильтрованного набора разделены: TotalSum — расход, IncomeSum — доход. ReceiptReportCandidateCounts использует общие правила начального окна и реальную открываемую копию, а не объединённые Accounts документа.

ReceiptDocumentReportProjection для деталей и успешного refresh читает доступные копии той же identity с MoneyMovementLinks/MoneyMovement/Account/Members. Агрегаты считают каждый видимый ID операции один раз, как список. Отсутствие ожидаемого набора — явная ошибка, не нулевой агрегат. Отказ доступа предшествует workflow. Ручной refresh читает исходный снимок без tracking и передаёт явный ID пользователя; workflow повторно проверяет доступ перед записью. Последующие отчётные чтения не получают общий snapshot автоматически.

RefreshPendingReceiptsUseCase получает IServiceScopeFactory, не общий UoW прохода. Выборка no-tracking ограничена 32 записями и упорядочена по CreatedAtUtc/Id; курсор использует те же поля и верхнюю границу времени начала прохода. Scope выборки освобождается до обработки, каждый документ получает отдельный async scope. Курсор продвигается и после неизвестного отказа: документ не блокирует следующие и не повторяется в том же проходе. Неизвестная ошибка логируется; после disposal только retry-state сохраняется в новом scope с проверкой версии/расписания. Ошибка записи retry-state логируется отдельно, следующие документы продолжаются. Отмена входного token останавливает проход без попытки. Scope выборки разрешает только IReceiptRepository; workflow документа использует IReceiptRefreshUnitOfWork. Повтор retry-state по-прежнему выполняется в новом scope.

Список и детали сохраняют чтение собственного чека. Счета, связанные операции, их суммы и фильтры DTO ограничиваются текущим владением/участием через FinancialDataAccess. Для маппинга агрегатов загружать Account/Members связанных операций; авторство операции само по себе не даёт доступа. Скрытые привязки не активируют правило подбора для чека без счёта.

ReceiptReadQueries выбирает фискальные документы до Skip/Take, считает count/доход/расход полного фильтра и загружает граф только копий выбранных документов. Поиск использует представителя с приоритетом редактируемой копии и устойчивым строковым ID, как mapper. Счётчики запрашиваются только для отображённых реальных ReceiptId. Legacy GetReceiptListUseCase сохранён без UI-потребителя и возвращает полный период; экран использует GetReceiptListPageUseCase. Несколько запросов не образуют snapshot.

## Проверка

Подходящие изолированные проверки находятся в tests/CostVision.Application.UnitTests. Собирать конкретный затронутый .csproj по корневым правилам; mock-репозитории не подтверждают SQL.

## Сопровождение

Этот файл отвечает за собственные исходники непосредственно в данной папке; для дочерних папок действуют их локальные инструкции и общие правила родителей. После изменения исходников в этой папке сверить и актуализировать здесь ответственность, контракты, зависимости и способ проверки в рамках той же задачи. При переносе файлов обновить описания прежней и новой папок. Не добавлять фиктивный журнал или неподтверждённый результат проверки.

Общая карта и порядок сопровождения: [техническое руководство](../../../../Documentation/TechnicalGuide/12-source-map-and-maintenance.md). Открытые изменения: [план рефакторинга](../../../../Documentation/Plans/project-refactoring-2026-10-13/README.md).

Ручной/QR-ввод проверяет форму до доступа/записи. Оба списка проверяют календарный период до чтения. Кандидатные счётчики возвращают Validation, когда день ±1 с исключительной верхней границей не представим. Identity, строки QR и сохранение этой проверкой не меняются.
