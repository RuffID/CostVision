# Проекции чеков

## Ответственность

ReceiptMapper и ReceiptGroupMapper преобразуют сущности и группы фискальных копий в DTO.

## Контракты и границы

ReceiptMapper требует явный ID текущего пользователя, фильтрует счета и связанные операции по текущему владению/участию. Счётчики и суммы используют только видимые связи. ReceiptGroupMapper объединяет уже доступные чеки и их отфильтрованные DTO; автор не подставляется как текущий пользователь автоматически.

HasAccountLinks сохраняет внутри Application различие между настоящим чеком без счёта и чеком со скрытыми привязками. Группа объединяет этот признак; он не сериализуется в JSON и не раскрывает счёт.

Представитель группы сохраняет приоритет редактируемой копии, затем ordinal-строковый ID. При одинаковой роли размещения используют ReceiptId, счета — Name/Id. SQL-поиск страницы использует ту же политику представителя; открываемый ReceiptId по-прежнему выбирается из доступных объединённых размещений.

## Проверка

ReceiptMoneyMovementAggregates считает доступные операции по уникальному ID среди доступных копий документа; одинаковые дата/сумма не объединяют разные платежи. Для корректного расчёта нужны загруженные MoneyMovement/Account/Members. Та же проекция применяется группой списка и дополнительным чтением деталей/refresh. OperationType передаётся явно, номинал документа остаётся положительным.

Подходящие изолированные проверки находятся в tests/CostVision.Application.UnitTests. Собирать конкретный затронутый .csproj по корневым правилам; mock-репозитории не подтверждают SQL.
