# Граница прикладных сценариев

## Ответственность

Проект объединяет use case, запросы, DTO, ServiceResult и порты хранения/сервисов. Он зависит от Domain и фактически от EF Core/EFCoreLibrary через базовый контекст.

## Контракты и границы

Доступ и бизнес-правила выполняются в сценариях; многозаписные изменения — через IUnitOfWork. Не переносить сюда SQL-provider, HTTP PageModel или детали конфигурации среды.

Идентичность документа ReceiptIdentity отличается от копии автора и связи со счётом. Сценарии записи чеков запрашивают явную Serializable-изоляцию через UoW; известный конфликт хранения возвращается как Conflict. Базовые predicate/include остаются на стороне Application.

Импортный ключ банковской строки отличается от ID операции и счёта размещения. Импорт, создание/автоматическая сверка, ручная привязка и перенос координируются в Application через Serializable и явное сохранение. Несовместимые денежные связи запрещают перенос до мутации; скрытая отвязка недопустима. Эти границы не доказывают отсутствие SQL-гонки без отдельной приёмки.

Изменение общих названий каталога требует явного текущего пользователя и доступной покупки. Назначаемые роли проверяются до мутации профиля. Создание чеков/операций и сохранение импорта запрещены в архивный счёт; это правило не переносится на исторические изменения.

Область финансового чтения задаёт `Extensions/FinancialDataAccess`: счёт и операция требуют текущего владения/участия, собственный чек остаётся доступным автору. Вложенные DTO и агрегаты используют явный ID текущего пользователя; Admin не расширяет эту область. Предикаты и include продолжают компоноваться в вызывающих use case.

## Проверка

Отчёты суммируют доступные документы по ReceiptIdentity и реальные платежи по ID. Чистый расчёт dashboard получает уже ограниченный набор; правила направлений и единиц общие в ReceiptFinancialRules. Детали/refresh дополнительно читают доступные копии только для денежных агрегатов; workflow обновления и его конкурентность этим не защищены.

Подходящие изолированные проверки находятся в tests/CostVision.Application.UnitTests. Собирать конкретный затронутый .csproj по корневым правилам; mock-репозитории не подтверждают SQL.
