# План внедрения операций

## Термины

Название зафиксировано:

- В пользовательском интерфейсе использовать "Операция".
- В коде использовать `MoneyMovement`.

Такое разделение нужно, чтобы не путать новую сущность с уже существующим `ReceiptOperationType`, который описывает тип фискального чека.

## Вопросы и возможные противоречия

1. `Account` должен постепенно стать финансовым счётом с балансом. Сейчас он работает как хранилище/группа доступа для чеков, но новая модель операций должна развивать его в сторону счёта, у которого баланс рассчитывается по операциям за период и может быть положительным или отрицательным.
2. Расход/приход можно определять по знаку введённой суммы, но в БД хранить нормализованную положительную сумму и отдельный тип операции.
3. Наличные операции не имеют банковской карты и внешнего идентификатора, поэтому импортные и банковские поля должны быть необязательными.
4. Связь операции и чека делать многие-ко-многим: у операции может быть несколько чеков, один чек может быть привязан к нескольким операциям.
5. Операцию производит конкретный человек и привязывает её к счёту. Для этого в `MoneyMovement` нужен `CreatedByUserId` и отдельное поле участника/владельца операции, например `OwnerUserId` или `PerformedByUserId`. Название поля нужно выбрать при реализации.
6. Поиск подходящих чеков по умолчанию должен использовать временное окно 1 час, но фильтр по времени должен отключаться галочкой. Также нужны поля выбора периода и фильтрация по суммам.
7. Импорт банковской выписки проектировать как отдельный источник операций. В модели нужен явный признак происхождения операции: ручное добавление или импорт банковской выписки.

## Распределение суммы

Под "распределением суммы" имеется в виду не сама привязка чеков к операции, а хранение того, какая часть суммы операции относится к конкретному чеку.

Пример: одна операция на 3000 рублей может быть связана с двумя чеками на 1000 и 2000 рублей. В этом случае привязок достаточно. Но если операция на 3000 рублей связана с одним чеком на 5000 рублей, может понадобиться указать, что к операции относится только 3000 из этого чека.

На первом этапе сумму распределения не добавлять. Сделать только связь `MoneyMovement` - `Receipt`. Если позже появятся частичные оплаты, расщепление расходов между людьми или компенсации, добавить сумму в связующую сущность.

## Этап 1. Ручное добавление и список операций — выполнено

1. Добавить доменную сущность операции:
   - идентификатор;
   - `AccountId`;
   - нормализованная положительная сумма;
   - тип: расход / приход;
   - дата и время операции;
   - комментарий;
   - `CreatedByUserId`;
   - владелец/исполнитель операции: `OwnerUserId` или `PerformedByUserId`;
   - `CreatedAtUtc`, `UpdatedAtUtc`;
   - источник операции: ручное добавление / импорт банковской выписки.
2. Добавить enum типа операции. Значения лучше назвать нейтрально: `Expense`, `Income`.
3. Добавить enum источника операции. Значения лучше назвать `Manual`, `BankStatementImport`.
4. Для импортированных операций заполнять `Comment` текстом операции из таблицы выписки. Отдельные служебные поля с данными импорта не добавлять.
5. Добавить EF configuration. Миграцию не создавать агентом: её создаёт пользователь вручную через консоль после изменения модели.
6. Добавить тонкий репозиторий операции по текущим правилам проекта, без методов вида `GetByAccountWithReceipts`.
7. Добавить use case:
   - создание операции;
   - получение списка операций за период;
   - получение доступных счетов для формы;
   - проверка доступа пользователя к счёту.
8. Добавить Razor Page для операций:
   - форма добавления;
   - список операций на этой же странице;
   - фильтр по периоду и счёту;
   - AJAX handlers через `ServiceResult` и `JsonResultMapper`.
9. Добавить TypeScript-модули страницы:
   - `api.ts`;
   - `types.ts`;
   - `state.ts`;
   - `render.ts` / `ui.ts`;
   - `index.ts`.
10. В UI разрешить ввод суммы с минусом, но на backend нормализовать:
   - сумма `-500` => тип `Expense`, сумма `500`;
   - сумма `500` => тип `Income`, сумма `500`;
   - если пользователь явно выбрал тип, знак суммы можно использовать только как подсказку или валидацию.

## Этап 2. Импорт банковской выписки

Базовый поддерживаемый формат импорта на первом этапе - PDF-выписка с текстовым слоем.

Правило структуры PDF-выписки:

1. В начале документа находится шапка выписки: дата формирования, владелец, номер договора, начальный баланс на дату, итоговые суммы поступлений, расходов и кэшбэка, конечный баланс на дату. Шапку не импортировать и не сохранять, она нужна только как ориентир для поиска начала таблицы операций.
2. Далее идут табличные блоки операций по картам. Каждый блок начинается строкой вида "Операции по карте № ...", содержит маскированный номер карты, имя держателя и итог расходов по этой карте.
3. После заголовка блока идут операции с колонками:
   - дата и время операции;
   - дата обработки;
   - сумма в валюте счёта;
   - описание;
   - сумма операции.
4. Одна операция занимает несколько строк текста: сначала дата/время операции, дата обработки и две суммы, затем одна или несколько строк описания.
5. Если время операции отсутствует, строка содержит только дату. Для импорта такую дату считать датой операции без точного времени.
6. Положительные суммы имеют префикс `+` и импортируются как `Income`; суммы без плюса импортируются как `Expense`.
7. Описание операции импортировать в `Comment`. Отдельно исходный текст операции, номер договора, маску карты и держателя карты не сохранять.
8. Дедупликацию при предпросмотре делать по фактическим полям операции: дата операции, дата обработки, сумма, тип операции и комментарий. Отдельный fingerprint в модели не хранить.
9. Повтор заголовков таблицы на новой странице не считать новым блоком операций. Новый блок начинается только с заголовка карты.
10. Итоговые строки шапки и строки "Расходы: ..." внутри карточного блока не импортировать как операции.

Техническое правило парсинга PDF:

1. Извлечь текст постранично и нормализовать строки:
   - обрезать пробелы по краям;
   - удалить пустые строки;
   - заменить повторяющиеся пробелы одним пробелом;
   - сохранить порядок строк внутри страницы.
2. Шапку выписки пропускать. Парсер не должен создавать операции из строк баланса, поступлений, расходов и кэшбэка.
3. Новый блок операций начинать при строке, которая начинается с `Операции по карте №`. Маску карты и держателя карты можно использовать только во время парсинга как границу блока, но не сохранять в модель операции.
4. Строки заголовков колонок пропускать по набору маркеров: `Дата и время`, `операции`, `Дата`, `обработки`, `Сумма`, `в валюте счёта`, `Описание`, `операции`.
5. Строку операции определять регулярным выражением даты в начале строки: `^\d{2}\.\d{2}\.\d{2}( \d{2}:\d{2})?$`.
6. После найденной строки даты операции ожидать следующий порядок непустых строк:
   - дата обработки: `^\d{2}\.\d{2}\.\d{2}$`;
   - сумма в валюте счёта: `^\+? ?[\d ]+,\d{2} ₽$` или `^\+? ?[\d ]+\.\d{2} ₽$`;
   - сумма операции: такой же формат суммы;
   - описание: все следующие строки до следующей даты операции, нового блока карты, повторного заголовка таблицы или конца документа.
7. Суммы парсить с учётом пробелов-разделителей тысяч и десятичного разделителя `.` или `,`. Символ `₽` не хранить в числовом значении.
8. Тип операции определять по первой сумме: если сумма начинается с `+`, это `Income`, иначе `Expense`. В модель сохранять положительное значение суммы.
9. Описание склеивать через пробелы в одну строку без переносов и сохранять в `Comment`.
10. Если строка не попадает в ожидаемый порядок, не импортировать её молча: добавить ошибку строки в результат предпросмотра.

Пример шапки выписки с вымышленными данными. Шапка не импортируется и не сохраняется:

| Выписка по договору №1234567890 | |
| --- | ---: |
| Баланс на 01.04.26 | 12 345.67 ₽ |
| • Поступления | 45 000.00 ₽ |
| • Расходы | - 18 765.43 ₽ |
| • Кэшбэк | 120.00 ₽ |
| Баланс на 30.04.26 | 38 700.24 ₽ |

В PDF эта шапка может извлекаться не как таблица, а как последовательность строк. Парсер должен пропустить её и начинать импорт только с таблицы операций.

Пример распознанной таблицы с вымышленными данными:

| Дата и время операции | Дата обработки | Сумма в валюте счёта | Описание | Сумма операции |
| --- | --- | ---: | --- | ---: |
| 01.04.26 09:15 | 01.04.26 | 734.50 ₽ | Оплата в MARKET Novosibirsk RUS | 734.50 ₽ |
| 02.04.26 | 02.04.26 | + 15 000.00 ₽ | Внутрибанковский перевод с договора 1234567890 | + 15 000.00 ₽ |
| 03.04.26 18:40 | 03.04.26 | 1 280.00 ₽ | Внешний перевод по номеру телефона +79990000000 | 1 280.00 ₽ |

Оставшиеся задачи по импорту:

1. На странице операций добавить зелёную кнопку "Импорт", которая открывает модальное окно работы с импортом.
2. Сделать application service парсинга выписки, который возвращает промежуточные DTO, а не сразу пишет в БД.
3. В модальном окне добавить предпросмотр:
   - распознанные операции;
   - потенциальные дубли;
   - ошибки строк;
   - выбор счёта для импорта.
4. Добавить сохранение импортированных операций через use case и `IUnitOfWork.ExecuteInTransaction`.
5. Для других банковских форматов позже добавить отдельные парсеры Excel/CSV/PDF с тем же промежуточным DTO.

## Этап 3. Связь операций и чеков

1. Добавить связующую сущность между операцией и чеком.
2. На первом этапе достаточно связи многие-ко-многим:
   - `MoneyMovementId`;
   - `ReceiptId`;
   - `CreatedByUserId`;
   - `CreatedAtUtc`.
3. Позже при необходимости добавить сумму распределения, если один чек или одна операция делится на части.
4. Добавить use case поиска подходящих чеков:
   - доступные пользователю чеки;
   - тот же счёт или пересечение по доступному счёту;
   - сумма рядом с суммой операции;
   - временное окно 1 час по умолчанию;
   - возможность отключить фильтр по времени;
   - ручной выбор периода дат;
   - фильтр по сумме;
   - исключение уже привязанных чеков, если повторная привязка не нужна.
5. Добавить на странице операции детальный режим:
   - открытие операции;
   - список уже привязанных чеков;
   - список кандидатов;
   - кнопки привязать / отвязать.
6. В отчётах добавить фильтры:
   - операции без чеков;
   - чеки без операций;
   - операции с привязанными чеками;
   - расхождения суммы операции и суммы чеков.

## Общая рекомендация по модели

Не связывать чек с операцией напрямую через nullable `OperationId` в `Receipt`. Связующая таблица гибче и сразу покрывает случаи "одна операция - несколько чеков" и "один чек - несколько операций". Даже если UI сначала будет позволять только простую связь, модель не придётся ломать при следующем расширении.

Предварительные имена сущностей:

- `MoneyMovement` - операция.
- `MoneyMovementType` - тип операции: расход / приход.
- `MoneyMovementSource` - источник операции: ручное добавление / импорт банковской выписки.
- `MoneyMovementReceipt` - связь операции и чека.
